How to read this

Every decision below follows the same four beats, because the reasoning matters more than the choice:

Chosenwhat the system does
Whythe reasoning, including which other decision it pays off
Rejectedthe alternatives, and the specific reason each lost
Challengethe strongest objection I expect, and my answer to it

Two things worth knowing up front. First, several decisions pay for each other — the choice of query core (D3) is also the cost answer (D12), and reusing the Power BI model (D7) is also the access-control answer (D14). Where that happens I've said so, because a decision that solves two problems is the one worth defending.

Second, the honest boundary: this is built on synthetic data. It proves the logic, not the fit to any real terminal. Every claim about a client's numbers would need that client's data and their signed question set.

The architecture spine

"which berths had the worst crane idle time last month?"
   ↓
 scope + intent            is this answerable? which client? (client id from auth)
   ↓
 LLM → QueryIntent JSON    schema-validated, enum-bound to the registry
     { op: aggregate,
       metric: crane_idle_time_pct,
       grain: berth, sort: desc, limit: 5,
       time: last_complete_month }
   ↓
 METRIC REGISTRY (per client) → deterministic SQL compiler
     soft-delete filter · as-of pinning · alias + timezone resolution
   ↓
 warehouse → rows + lineage + freshness + completeness
   ↓
 graded answer card        CERTIFIED / QUALIFIED / CLARIFY / REFUSE
     number · definition used · as-of · restatement diff · what was excluded

The model appears exactly once, in the second step, and its only output is a small validated object. Everything that produces a number is deterministic and unit-tested.

Decision 1 — Scenario

D1 · SCENARIO CHOICE

Scenario 2, "Ask your terminal data" — not 1 or 3

The client-facing plain-English data product, built as a repeatable product rather than a one-off.

Why

  • Only scenario touching all four pillars. Strategy (why build it), Development (the pipes), Control (trust and definitions), Innovation (the agent) — so the answer doubles as a product proposal rather than a thought experiment.
  • It's the revenue-facing one. Scenarios 1 and 3 are internal.
  • Its four questions map onto things AYBI has already published. Repeatability ↔ their multi-terminal KPI-divergence problem. Trustworthiness ↔ Data Control's literal promise. "Useful, not an impressive demo" ↔ "clever vs useful" and "the real risk is building too soon."

Rejected

  • Scenario 1, data-quality investigation copilot — sharper questions, but it lands only on Data Control, stays internal, and carries no growth story. Its best ideas survive here anyway: the free-running investigation agent is exactly what I'd build for engineers (see D4).
  • Scenario 3, technical direction — matches the job title, but discards the terminal domain, which is AYBI's whole identity, and risks reading as slideware. Its substance is preserved in D15's 90-day plan.

"Why not Scenario 3? You're applying to lead."

Scenario 2 is the leadership answer with evidence attached. It forces the same calls — what ships first, what gates a release, how a BI-strong team gets productive — but grounded in a product a client would pay for. Leadership shown rather than asserted. The 90-day plan is in here; it just has a product attached to it.

Decision 2 — Deliverable

D2 · DELIVERABLE SCOPE

Deck plus a genuinely working demo plus a readable repo

Build it for real. The deck is the spine; a tight recorded clip carries the demo inside the 15 minutes; the live app and the repo are the proof and the backup.

Why

  • For a Lead AI Engineer, evidence of building beats description of building. Every candidate submits a deck.
  • Recorded clip over live app, inside the slot. Four questions in 15 minutes means a demo that hangs costs the whole slot. The recording is the senior move, not the timid one — the live app stays open for afterwards.
  • The repo runs from a clean clone with no cloud account, so they can verify it without me.

Rejected

  • Deck only — no proof of build.
  • Unconditional live demo — a time bomb, and it pulls the whole preparation toward polish-for-the-room, which is the demo-ware their fourth question warns about.

"Why not show it live?"

It is live — open it now if you like. The clip is in the deck so the 15 minutes goes to reasoning instead of a loading spinner. Reliability over theatre.

Decision 3 — Query core

D3 · QUERY CORE · the load-bearing decision

Governed semantic layer with a constrained compiler. The LLM never writes SQL.

The model emits a schema-validated QueryIntent — op (aggregate or diagnose), metric, grain, dimensions, filters, time window — whose fields are enum-bound to the client's metric registry. A deterministic compiler turns that intent into SQL. Unknown metric, ambiguous grain or missing time window means refuse and ask, not guess.

Why

  • It turns their promise into a mechanism. "The same question always gets the same answer" is only true if the definition lives in one governed place rather than in a model's head. Same question → same intent → same SQL → same number.
  • The hallucination surface collapses from "any SQL string" to "a closed enum". The model cannot invent a metric, a column or a join path, because it never names one — it picks one.
  • It's the only variant that is a product. The metric ontology is shared across clients; only the per-client mapping changes.
  • It makes evaluation exact. An intent is a small JSON object, so it diffs against a gold intent with no judge model involved (D11).
  • It makes caching possible at all (D12). Intents are canonical, so "worst crane idle last month" and "which berth was idlest in July" collapse to one cache entry. One decision pays off twice.

Rejected

  • Text-to-SQL with validate-and-repair — the dominant failure isn't SQL that errors, it's SQL that executes fine and is quietly wrong: wrong join grain, soft-deletes unfiltered, corrections double-counted. Invisible to the client, which is exactly the harm to avoid. It also needs re-tuning per client, so it can't be a product. Kept only as an internal engineer-review escape hatch, never client-facing.
  • Certified templates only — near-zero hallucination and very cheap, but brittle off-menu and structurally unable to answer a "why" question. Folded back in as a caching tier instead of the core.
  • Hybrid as the headline — this is what production actually looks like, but explaining three routers in 15 minutes buries the idea. Presented as "the core, plus a certified-answer cache in front of it".

"Isn't this just a slower text-to-SQL with extra work? Real clients ask things your registry doesn't cover."

They do, and that's the feature. When a question falls outside the registry the honest answer is "I can't answer that yet, here's what I'd need" — not a plausible number. Every gap is logged as a metric request, so the registry grows from real demand. Coverage becomes a roadmap input instead of a runtime gamble. You'd never let a BI tool invent a KPI definition at runtime; this is the same rule.

"Who writes the registry? That's consulting work, per client."

It is, and it's work AYBI already sells and already does — this makes it reusable instead of throwaway. The canonical terminal metric set ships with the product; per client you map, you don't redefine. That's the 3× faster delivery claim made concrete. And see D6: the mapping is drafted by a model and reviewed by a human.

Decision 4 — Why-questions

D4 · DIAGNOSIS

Deterministic decomposition. The LLM narrates, it never concludes.

A fixed diagnose routine runs in code and produces ranked evidence. The model turns that evidence into prose and is required to label the items contributors, not causes.

diagnose(metric=dwell_time, entity=reefer, window=2024-W12)

1  IS IT REAL?
   ✓ freshness ok   ✓ 12 late corrections landed W12+3d
   → spike survives correction replay: YES  (as-of vs latest)

2  CONTRIBUTION TO +4.2h DELTA
   berth B3 ............... +2.6h  (62%)
   customs hold flag ...... +0.9h  (21%)
   reefer plug shortage ... +0.4h  (10%)
   other / unexplained .... +0.3h   (7%)

3  CORRELATED SIGNALS  declared in the registry, never inferred
   • B3 crane 2 downtime 14h, W12    • vessel MSC-x arrived +19h late

→ the model narrates the above. It never upgrades a contributor to a cause.
→ the unexplained remainder is always shown, never hidden.

Why

  • Step 1 exists because in this data the likeliest explanation for a spike is the data, not the operation. Late corrections and soft-deletes are named in the brief. A system that reports a spike caused by a restatement has actively misled the client.
  • Every number comes from code, so it is reproducible, unit-testable and identical on re-run. The model contributes language, not findings — the only division of labour that survives a model swap.
  • Contribution analysis is arithmetic, not inference. It's defensible in front of an operations manager because you can point at the rows.
  • Showing the unexplained remainder is the trust move. A system that always fully explains the delta is lying, and operators know it.

Rejected

  • Refuse all why-questions — the brief names one as a target use case. Kept as the fallback when decomposition finds no material contributor: "no single factor explains this, here's the spread."
  • Free-running agentic investigation — two runs produce two different stories, cost and latency are unbounded, and it can't be regression-tested. That's Scenario 1's internal engineer copilot, where a human reviews every word. Not a client product.
  • Curated causal playbooks per client — the strongest version, and very AYBI (domain fluency as the moat). But the playbooks would have to be invented for a demo, and inventing terminal expertise in front of people who have 50+ terminals of it is a bad trade. Presented as the roadmap step instead: playbooks are co-written with terminal ops, and step 3 already has the slot for them.

"Contribution analysis isn't causation. So what has the AI actually added?"

Agreed, and the product says so out loud. What it adds is the hour a planner would have spent slicing dashboards to discover that B3 is 62% of it. Same conclusion they'd have reached, in seconds, with its own uncertainty attached. The causal call stays with the person who knows the yard.

"Why not let the agent investigate freely? That's the interesting part."

Because I can't put a number on how often a free-running investigation is wrong, and I won't ship what I can't measure onto client data. The bounded version has a regression suite. I'd happily run the free version internally, where an engineer reviews it before anyone acts.

Decision 5 — Messy data

D5 · TIME SEMANTICS

Bitemporal warehouse, as-of answers, visible restatement diff

Solved in the model, not in the agent. Two clocks everywhere: event_time (when it happened in the yard) and knowledge_time (when the warehouse learned it). Data Vault satellites already carry the load timestamp, so this is exposure, not new plumbing. Soft-delete filtering lives in the compiler, never in a prompt.

ANSWER CARD
  Worst berth, crane idle, March 2024
  → B3, 11.4%
     as of         2024-04-02 06:10
     restated      since you last asked  (was 12.1%)
     why changed   9 late gate events + 2 reversals
     excluded      31 soft-deleted rows
     completeness  98.7% of expected moves present

Why

  • Reproducibility. Any past answer can be replayed exactly by pinning knowledge_time — which is what an audit, a dispute, or a post-mortem on a bad decision actually requires.
  • The restatement diff turns the scariest property of this data into a trust feature. The alternative — two people asking the same question a week apart and silently getting different numbers — is precisely how confidence is lost.
  • It isn't promptable. Soft-delete exclusion enforced in a compiler is enforced 100% of the time. The same rule in a system prompt is enforced most of the time, and you never learn which questions were the exception.
  • The line this earns: most of trustworthiness here is not an LLM problem. It's modelling, lineage and definitions — Data Development and Data Control. AYBI's existing business, so the AI layer extends what they already sell rather than detouring from it. Jeffrey Slort's "we focus on what's foundational", applied.

Rejected

  • Latest state only, with a staleness warning — simpler, but same-question-different-answer with no explanation undermines the entire pitch.
  • Freeze windows, only answer settled periods — safe, but it guts the use case; terminal decisions are intraday. Retained as a per-metric confidence rule rather than a global gate.
  • Handle it in the system prompt — kept in the deck deliberately, as the anti-pattern slide. Correctness that depends on a model remembering a rule is not correctness.

"Our warehouse isn't fully bitemporal for every source. Now what?"

Then the registry says so per metric and the answer card degrades honestly: "as-of replay unavailable for this metric, latest state only." Coverage becomes visible instead of assumed, and closing it is a scoped ticket with a client-visible payoff. That's a better position than pretending uniformity.

Decision 6 — Repeatability

D6 · MULTI-TENANCY · the headline idea

Canonical ontology, thin per-client mapping — and the model drafts the mapping

Ship a canonical terminal metric ontology with fixed semantics. Per client, write only a mapping — which table, which column, which soft-delete flag, which timezone, which aliases — never a new definition. An LLM drafts that mapping from the client's schema, sample rows and legacy report SQL, flagging ambiguities as explicit questions. A BI engineer reviews and signs it off before anything goes live.

SHARED (the product)        PER CLIENT (config, reviewed)
canonical metrics             mapping.yml  (~200 lines)
intent schema                 berth naming / aliases
compiler                      soft-delete flag + timezone
diagnose routines             freshness SLAs
eval harness                  gold Q&A set (client-signed)
answer-card UI                declared signals

ONBOARDING
1  LLM reads schema + sample rows + legacy report SQL
2  drafts mapping.yml, flags ambiguities as QUESTIONS
3  BI engineer reviews, corrects, signs off        ← the gate
4  gold set runs green  →  client sees it

Model wrong here  → a human catches it at review.
Model wrong at runtime → a client makes a bad call.

Why

  • The inversion is the headline. The highest-leverage use of the LLM in this product is onboarding, not answering. Same technology, moved to where being wrong is cheap and a human catches it.
  • It makes "repeatable" measurable — onboarding days per client, and percentage of the drafted mapping accepted without edit. Those numbers turn this from a demo into the 3× faster delivery claim, stated in AYBI's own units.
  • It preserves cross-terminal benchmarking, because metric semantics are identical everywhere. For a 23- or 50-terminal operator that's plausibly worth more than the chat interface.
  • It respects their published finding that terminals under the same owner define KPIs differently: you map their language to canonical meaning, you don't ask them to change.

Rejected

  • Hand-written mapping only — kept as the graceful fallback. The mapping format is the real asset either way; the model just fills it faster.
  • Per-client registry with no shared ontology — the one-off the brief explicitly rules out, and it forfeits benchmarking.
  • Force clients onto one global model — a change-management programme, not a product. It stalls on client one.

"You've moved the hallucination risk from runtime to onboarding. A wrong mapping is wrong for every question after it, forever."

Correct — and that's exactly why a human sign-off gate is mandatory there and nowhere else. A wrong mapping is also a wrong mapping a human can see: 200 lines of YAML, diffable, reviewed once, with a client-signed gold question set that fails loudly if it's wrong. Compare a runtime error — invisible, unrepeatable, and delivered straight to the client. I'd rather concentrate risk somewhere it can be reviewed than spread it thinly where it can't.

"Who owns the canonical definitions? Terminals will disagree with them."

AYBI owns them, and that's a commercial asset. It's the same authority a consultancy already exercises when it tells a client their two dwell-time numbers can't both be right. Where a client genuinely differs they get a client-scoped variant, explicitly marked non-benchmarkable — so the disagreement is named rather than buried in two dashboards.

Decision 7 — Metric source of truth

D7 · DEFINITIONS

Generate the registry from the existing Power BI semantic model

Don't author a second set of KPI definitions. The Power BI semantic model is already the governed layer AYBI has been paid to build — measures, relationships, row-level security, business names. Sync the registry from it read-only (XMLA / TMDL / INFO.VIEW.MEASURES) and execute against it where appropriate. AYBI-authored YAML adds only what Power BI has no concept of: intent enums, diagnose routines, freshness SLAs, as-of policy, aliases. A CI drift check compares registry to model and fails loudly.

ONE DEFINITION OF TRUTH

  Power BI semantic model   already governed, already sold
    measures / DAX │ relationships │ RLS │ business names
          │
          │  sync via XMLA / TMDL   (read-only)
          ↓
  metric registry (generated)  +  AYBI-authored additions:
        intent enums │ diagnose routines │ freshness SLA
        as-of policy │ aliases
          │
          ↓
  compiler → SQL (warehouse direct)  or  DAX (via XMLA)
          ↓
  answer == dashboard number.  RLS inherited, not rebuilt.

Drift check runs in CI: registry vs model. Fails loudly.

Why

  • It extends "same question, same answer" to include the dashboard. The agent's number equals the dashboard's number by construction, not by discipline. Their own words for the failure this prevents: "questioning whether that five should be a six."
  • Access control comes for free and correct. The agent inherits existing RLS instead of me reinventing per-client permissions — which is otherwise the single most likely way this product leaks one terminal's data to another (D14).
  • It uses what exists. "We don't rebuild everything from scratch" is their sentence, and arriving with a stack migration reads as not listening.
  • The generated-vs-authored split is honest about where the work is: the LLM-specific assets are small, and the governance asset already exists.

Rejected

  • Own YAML registry, warehouse-direct — cleaner to build, and the necessary fallback for clients without Power BI. As the default it puts two definitions of dwell time in the building. If used, a drift test against the dashboard is mandatory.
  • dbt / MetricFlow as source of truth — genuinely the better multi-client end-state. Presented as the 12-month direction, not the plan, because it presumes dbt and amounts to proposing a platform migration.
  • Cube or AtScale — new vendor, new licence, new thing for a BI-strong team to learn, and largely duplicates their Power BI models.

"XMLA is slow and DAX generation is its own hallucination surface. Why not just hit the warehouse?"

Both paths exist and the registry decides per metric. Warehouse-direct SQL is the default for speed; the Power BI model is the definition authority, and the execution path only when a measure's logic is non-trivially DAX. What matters is that one is derived from the other and CI proves it — rather than two teams maintaining dwell time independently and discovering the divergence in front of a client.

"What about a client who doesn't use Power BI?"

Then the registry is hand-authored against their marts — same format, same compiler, same evals. The pattern doesn't depend on Power BI, it depends on there being exactly one governed definition per metric. Power BI is just where AYBI's clients already keep theirs.

Decision 8 — Build stack

D8 · IMPLEMENTATION

Python + DuckDB + FastAPI, with a hand-built answer-card UI

Synthetic terminal data in DuckDB with bitemporal columns. A real TMDL parser fed a sample Power BI export, so D7 is working code rather than a claim. One page whose entire job is the answer card.

repo/
  data/       synthetic terminal generator + duckdb
              bitemporal, 2 terminals, seeded mess
  registry/   canonical_metrics.yml
              clients/tos_alpha.yml  tos_beta.yml
              from_tmdl.py           ← real TMDL parser
  core/       intent.py  compile.py  diagnose.py
              grade.py  cache.py  providers.py
  evals/      gold_intents.jsonl  gold_answers.jsonl
              traps.jsonl  run_evals.py
  api/        main.py (FastAPI)
  web/        index.html  app.css
  DECISIONS.html   README.md

make demo → seeded db + server + browser

Why

  • Runs on any laptop with no cloud account, so the demo can't fail on someone else's tenant — and they can clone and run it themselves, which beats a video.
  • The answer card is the product, so the UI effort goes exactly there: number, definition used, as-of, restatement diff, completeness, refusal. Hand-built because default widget styling would undersell the only thing worth looking at.
  • DuckDB gives real SQL and real bitemporal queries with zero infrastructure.
  • Honest constraint: Power BI Desktop is Windows-only and the build machine is macOS, so a live tenant sync wasn't possible in three days. The parser is real; the export it reads is a sample. That's a laptop limitation, not an architectural one.

Rejected

  • Streamlit — saves a day, looks like a prototype, and renders the trust argument in default widgets.
  • Azure + Fabric + a live Power BI model — highest fidelity, but a tenant, a licence and Windows-only authoring, with nothing to show if it misbehaves on the day. Shown as the target deployment diagram instead.
  • Notebook only — doesn't demonstrate shipping a product surface.

"DuckDB isn't our stack. Does any of this transfer?"

The compiler emits SQL against a registry-declared dialect — DuckDB here, Synapse/Fabric or the Power BI model in production. Nothing in the intent schema, the diagnose routines or the eval harness is DuckDB-specific; it's swapping an adapter. I chose it so you could run this today without me provisioning anything.

Decision 9 — Models

D9 · MODEL SELECTION

Opus 5 for intent, Sonnet 5 for handlers, open-source in parallel

Claude Opus 5 for intent extraction. Claude Sonnet 5 for handler work — narration, clarifying questions, diagnose write-ups. A pluggable provider layer with a local open-source path (Ollama) so anyone without Claude access can run the repo, documented as reproducibility mode with expected quality degradation.

Why

  • Intent extraction is the one unrecoverable step. Every downstream number is right or wrong depending on it, and a wrong-but-plausible intent produces a confidently wrong answer. Spend the best model there.
  • The cost objection is answered by caching, not by a cheaper model. Intents are canonical, so the cache keys off the intent rather than the phrasing. The expensive call happens only on genuinely novel phrasings, so Opus-per-question is not Opus-per-request (D12).
  • Narration is bounded rewriting over evidence produced in code, so Sonnet 5 is sufficient by design. Where a mid-tier model suffices, that's the architecture working.
  • The open-source path does triple duty: reviewers can actually run the project, it demonstrates no vendor lock-in, and it pre-answers EU data residency for European logistics clients (D14).

Rejected

  • One model everywhere — leaves the routing win unused on a question the brief asks directly.
  • Haiku for intent — cheapest, but see the unrecoverable-step argument.
  • Open-source only — hosting and quality work that doesn't fit three days.

"Opus on every question is expensive at scale."

It isn't on every question — it's on every novel question. The intent cache is keyed on the canonical intent, so repeats and rephrasings never reach the model. I'll show the measured hit rate and cost per answered question rather than assert it. And if the numbers disagree with me, the provider layer means downgrading intent to Sonnet is a config change with an eval suite to prove it's safe.

"Why does filling in an enum need a frontier model?"

For clean questions it doesn't. It's for the messy ones, where the right output is a clarifying question rather than a guess. Knowing that a question is underspecified is the hard part, not filling the slots — and that's where smaller models were weakest. That's a claim I want the eval suite to keep honest as models change.

Decision 10 — Trust grading

D10 · TRUSTWORTHINESS

Four grades, decided in code, shown on every answer

● CERTIFIED● QUALIFIED ● CLARIFY● REFUSE

Every answer carries a badge whose grade is computed by deterministic checks — never by model self-assessment.

✓ metric in registry & client-mapped
✓ freshness within SLA            (28m / 30m)
✓ completeness ≥ threshold        (99.1%)
✓ window closed to corrections    (W12 settled)
✓ intent matches a signed gold question
✓ unexplained remainder < 20%     (diagnose only)

all pass   → CERTIFIED   cleared for operational decisions
1–2 soft   → QUALIFIED   answer, plus the named limitation
ambiguous  → CLARIFY     asks exactly ONE question back
no basis   → REFUSE      states what it would need

Silence about doubt is the bug.

Why

  • It answers the question as asked. "A wrong answer could mislead an operational decision" is addressed by making which answers are safe to act on an explicit checkable property, rather than an impression created by fluent prose.
  • Deterministic grading is regression-testable and survives model swaps. A model-reported confidence number can't be defended to an operations manager or held stable across versions.
  • The grades create a usable contract: certified answers can drive a berth call, qualified ones name their limitation, refusals become registry roadmap.
  • CLARIFY asks exactly one question. Operators won't complete an interrogation; a system that asks three questions gets abandoned.

Rejected

  • Always answer with caveats — uniform presentation pushes the risk assessment onto the reader every time, and caveats that appear on every answer are skipped by week two.
  • LLM self-reported confidence — poorly calibrated, drifts silently on model change, indefensible in front of a client.
  • Human certifies every answer — kills the real-time value and doesn't scale. Retained as the pilot gate: the first weeks run human-in-the-loop, and the thresholds above are calibrated from what reviewers actually corrected (D15). That's how thresholds get earned instead of guessed.

"Who's liable when a CERTIFIED answer turns out wrong?"

AYBI is, and that's the point of the word. It should only appear when the answer is reproducible from a signed definition on data that has settled — so a wrong certified answer is a bug with an audit trail and a failing test to add, not a mystery. The alternative, a uniformly confident tone, carries that same exposure on every answer with no way to tell which. The badge is what makes the boundary statable at all.

"Clients will just ignore the badges."

Then the badge distribution tells me so. If 90% of real questions land QUALIFIED, the badge is noise and the registry has a coverage problem I should fix rather than paper over. I'd track grade mix per client weekly as a health signal on the product, not on the user.

Decision 11 — Evals

D11 · STAYING GOOD

Five layers, mostly non-LLM, gated in CI

LAYER          TESTS                       JUDGE
1 intent       gold_intents.jsonl          exact structural diff
2 compiler     golden SQL snapshots        pytest
3 end-to-end   known-truth synthetic       assert ==
4 must-refuse  traps / out-of-scope        assert grade
5 narration    faithfulness to evidence    LLM judge

GATE  any prompt / model / registry change
      → layers 1–4 green, no exceptions
      → layer 5 reported, not blocking

PER CLIENT  30–50 gold questions, client-SIGNED
             = acceptance contract + regression suite + sales artifact

TRAPS (layer 4)
  "best berth?"             → CLARIFY   best by what?
  "crane idle next month"   → REFUSE    no forecast
  "why is Rotterdam slow"   → REFUSE    not your data
  "dwell time yesterday"    → QUALIFIED still settling

Why

  • "Is it good?" gets a number that doesn't itself depend on a model. Layers 1–4 are ordinary software tests, which is what makes the gate credible rather than advisory.
  • Each layer isolates a distinct failure mode, so a red suite tells you where the regression is — intent drift vs compiler bug vs data change vs tone. One end-to-end score only tells you that something broke.
  • Synthetic data has known truth, so layer 3 asserts exact values. That's a real advantage of building the generator rather than borrowing a dataset.
  • Layer 4 is the differentiator. Nearly everyone tests happy paths. Testing that the system correctly declines is what makes refusal a guarantee instead of a hope — and it's the most memorable thing to show in a demo.
  • The client-signed gold set makes evaluation commercial: acceptance criterion, regression suite, and the thing that makes "we tested it" mean something to a buyer.

Rejected

  • LLM-judge end-to-end — a model certifying a model, both drifting, with no exact-number guarantee. Confined to tone and faithfulness, where approximate is fine.
  • Human review only — can't gate a deploy and won't catch a regression on question type 37. Kept as the source of new gold cases.
  • Online metrics only — means discovering wrong numbers via client complaints, on client decisions. Needed, but after the gate.

"Gold sets rot. Your CI goes green while the product gets worse."

Which is why the gold set has an inflow: every CLARIFY, every REFUSE and every corrected answer from the weekly sample review becomes a candidate case. I'd track gold-set growth alongside pass rate. A suite that hasn't grown in a month is a suite I've stopped trusting.

"You're testing on synthetic data. Real data will break it."

Agreed — synthetic proves the logic, not the fit. On real client data the same five layers run against that client's signed gold set. The mess I seeded into the generator — late corrections, soft-deletes, divergent berth naming, timezone drift — is modelled on what the brief describes, precisely so those paths are exercised before real data hits them. The generator is a test fixture, not evidence about a client.

Decision 12 — Cost & latency

D12 · AFFORDABLE AT SCALE

Four cache tiers with intent-keyed invalidation

T0  certified answer cache
    key = intent_hash + client + knowledge_watermark
    corrections land → watermark bumps → only affected answers die

T1  intent cache          key = normalised question text
    "worst crane idle last month"    ┬ same intent → no LLM call
    "which berth was idlest in July" ┘

T2  prompt cache          the registry context block

T3  precomputed aggregates for top-N intents
    hot path = lookup, not a warehouse scan

GUARDRAILS
  per-client monthly budget cap + alert
  cost & latency logged per answered question
  p50 / p95 latency split by cache tier

Why

  • The D3 architecture is the cost answer. Canonical intents are what make caching possible: with free-form SQL you can't safely cache, because you can't tell that two differently-worded questions are the same question.
  • Watermark-keyed invalidation is what ties cost to D5. A corrections-heavy dataset makes naive answer caching dangerous; keying on knowledge_time means a cached answer dies exactly when the data behind it changes, and no sooner.
  • Cost per answered question is the honest unit — it absorbs cache hits, retries and refusals, unlike cost per API call.
  • Per-client budget caps make spend predictable enough to price, which is what lets this go on a contract.

Rejected

  • LLM-call caching only — the model often isn't the expensive part; a scan over a busy terminal's event table is. And stale-cache risk is worst exactly here.
  • Measure first, no caching — a legitimate stance, kept as the framing around T0/T1 rather than instead of them, since the brief asks the question directly.
  • Precompute everything nightly — combinatorial explosion across dimensions, and it kills the intraday freshness that is the whole point.

"A cached answer is a stale answer. Terminals move in minutes."

Which is why the key contains the knowledge-time watermark rather than a TTL. A cached answer is only served while the data it was computed from is unchanged; the moment corrections or new events land, that key no longer exists. Same reason the card shows an as-of stamp — freshness is stated, not assumed. Where a metric's SLA is tighter than the cache can guarantee, the registry marks it uncacheable.

Decision 13 — Genuinely useful

D13 · USEFUL, NOT IMPRESSIVE

Measure the baseline before building anything

WEEK 0 — before a line of code
  shadow 2 planners + 1 ops manager for one week
  log: question │ who they asked │ minutes to answer today
  → becomes registry backlog + gold set + BASELINE

THEN MEASURE
  hours returned / week vs baseline        ← headline, their unit
  % of questions answered with no BI ticket raised
  "did this change what you did?"          one tap
  time-to-answer p50 vs baseline

THE DEMO-WARE TEST  the honest one
  week-6 weekly-active askers outside the project team

COVERAGE GAP
  every REFUSE / CLARIFY → ranked metric request list
  → the roadmap is written by users, not by me

Why

  • Without a pre-build baseline, "hours saved" is a number you invented. One week of shadowing makes every later claim defensible, and it costs a week, not a quarter.
  • The week-0 log is three artifacts for one effort: what to build, what to test, and what to measure against. Cheapest step in the plan, and it de-risks the most.
  • It answers their own warning — "the real risk in data projects is building too soon" — with a concrete first action rather than agreement.
  • Week-6 usage outside the project team is the honest demo-ware test. Sponsors always use it in week 1. If nobody else is asking questions in week 6, it's a demo — and I'd rather find that out in a pilot than in a rollout.
  • Reporting in hours returned speaks AYBI's existing language, so the result lands as a case study rather than a metrics dashboard.

Rejected

  • Usage analytics alone — measures curiosity as much as value. Included, not relied on.
  • A/B against dashboards — ops teams are too small for significance, and randomising access during live operations is a hard sell.
  • Qualitative interviews alone — catches what metrics miss, kept at weeks 2/6/12, but won't answer a CFO.

"A week of shadowing before you build? The client wants to see something working."

They see something working in the same sprint — the shadowing runs in parallel with platform work that has to happen anyway. What it buys is that the first thing they see answers a question they actually asked last Tuesday, instead of the question I guessed they'd ask. That's usually the difference between a pilot that gets adopted and one that gets politely praised.

Decision 14 — Security & isolation

D14 · NOT ASKED, BUT THEY WILL ASK

Defence in depth: tenant from auth, data treated as untrusted, EU-resident

TENANT   from the authenticated session, never from the question
         "show me Rotterdam's numbers" → REFUSE, not a cross-read
QUERY    runs as the user's effective identity → RLS applies (D7)
PROMPT   registry + intent = instructions
         data values  = evidence block, never instructions
MODEL    EU region endpoint │ no training │ no retention
         Ollama path for clients who won't use a US vendor (D9)
LOGS     question + intent retained; row values redacted
DEPLOY   shared by default, single-tenant on request
TEST     cross-tenant probes are layer-4 eval cases (D11)

Why

  • Tenant from auth, not from language, means the isolation guarantee doesn't depend on the model interpreting a question correctly. Asking for another terminal is a refusal, not a permission check that might pass.
  • Inheriting Power BI RLS means access control is the client's existing audited model rather than a parallel one I invented — the second-order payoff of not rebuilding.
  • Free-text fields are attacker-controlled text. Vessel names, berth remarks and comment fields flow through this system. If they reach the instruction part of a prompt, a remark field can steer the agent. Keeping data in a structured evidence block is the cheap structural fix.
  • Raising residency unprompted is the point: "European logistics clients" is the brief's own framing, and this is the question that stalls deals during security review, not after.
  • Cross-tenant probes as eval cases means isolation is regression-tested, not asserted.

Rejected

  • Power BI RLS alone — covers access, but not injection, retention or region, which is what a security review actually asks about.
  • Single-tenant by default — multiplies ops cost and drifts versions across clients. Offered as a paid option.
  • Defer to phase 2 — a Lead who doesn't raise residency unprompted looks like one who'd discover it in a client's security review.

"Structured-evidence separation is just prompt engineering. A determined injection still gets through."

It reduces the surface, it doesn't close it — which is why it isn't the only control. The one that matters is that the model's output is a constrained intent, not an action. Even a fully successful injection can only produce a QueryIntent, which the compiler validates against the registry and executes under the user's own RLS. There's no tool it can reach that reads another tenant's data. The architecture limits the blast radius; prompt hygiene just reduces the attempts that land.

Decision 15 — Rollout

D15 · 90 DAYS

Internal dogfood → one metric, one terminal, human-in-loop → widen → second client

wk 0     shadow planners → baseline + gold set + registry backlog

wk 1–3   registry + compiler + evals
         ONE metric family (dwell), ONE terminal

wk 3–5   AYBI engineers dogfood it on their own delivery work
         exit: eval layers 1–4 green, engineers prefer it to the dashboard

wk 5–9   client pilot — a human reviews every answer
         exit: certified answers survive review unedited ≥ agreed rate
         → this is how D10's thresholds get calibrated

wk 9–12  reviewer removed for the certified lane only
         second client onboarded
         exit KPI: ONBOARDING DAYS, not answer accuracy

Every gate is a number. Nothing advances on enthusiasm.

Why

  • Every gate is a number, which is the actual content of the phrase "production-grade".
  • What's being de-risked changes at each step: correctness, then trust, then repeatability. Trying to prove all three at once is how these projects fail quietly.
  • The human-review phase isn't ceremony — it's the only honest way to calibrate D10's thresholds. Reviewer corrections are the data that says where CERTIFIED sits.
  • Internal dogfood earns the right to face clients, and it doubles as team enablement: BI engineers meet LLM behaviour on work they already understand, which teaches far more than a training session.
  • The second client's KPI being onboarding days is what makes repeatability falsifiable. If client two takes as long as client one, it isn't a product yet, and I'd say so.

Rejected

  • Broad coverage on one terminal first — delays the repeatability proof, which is the brief's central requirement.
  • Two clients from day one — fastest route to a true abstraction, but it doubles the surface while you're still learning what the abstraction should be, and two unhappy pilots is worse than one happy one.
  • Straight to client pilot — the standard is "dependable enough to put in front of European logistics clients"; internal use costs weeks, not months.

"Twelve weeks to answer questions about dwell time. That's slow."

Weeks 1–3 produce a working system. What the rest buys is the right to remove the human from the loop, and that isn't a step you can shortcut on client operational data. I'd also rather say twelve weeks and deliver in twelve than say four. If speed is the constraint, the honest lever is narrowing scope further — one metric, one terminal, reviewer stays — not compressing the gates.

Appendix — what an LLM must not touch

Scenario 1 asks this outright; it belongs here too, because the boundary is the design. Everything in this list is deliberately unreachable by a model in this system.

Never the model's jobWhy, and who does it instead
Metric definitionsGoverned in the registry, derived from the Power BI model, human-signed. A model that can define a KPI at runtime can silently redefine one.
Arithmetic and aggregationThe compiler and the warehouse. Reproducible and unit-tested; a model's arithmetic is neither.
Soft-delete and correction filteringThe compiler. A rule in a prompt is followed most of the time, and you never learn which time it wasn't.
Access control and tenancyAuth session plus inherited RLS. Never inferred from the question's wording.
The trust gradeDeterministic checks. Self-assessed confidence is uncalibrated and untestable.
Causal conclusionsNobody, from this data. The system reports contributors; the person who knows the yard decides cause.
ForecastsOut of scope, and refused explicitly. A language model asked "what will idle time be next month" will answer, and it shouldn't.
Writing to the warehouseRead-only, always. There is no write path to reach.
Deciding what to do about itThe operator. The product returns an answer and its uncertainty, not an instruction.

What the model is for: mapping human language onto a governed intent, asking a good clarifying question when the ask is ambiguous, narrating evidence it did not produce — and, highest-leverage of all, drafting the per-client mapping at onboarding where a human reviews it (D6).
