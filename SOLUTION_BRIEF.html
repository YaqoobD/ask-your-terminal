A governed question-answering layer over messy multi-terminal data, built as a repeatable product rather than a one-off. Two pages. Detail in the repo.

The whole design in one sentence: the LLM picks; it never computes. It maps plain English onto a governed query intent. Every number, filter, trust grade and diagnosis is produced by code.

What the model does

  • Turns language into a governed intent
  • Asks one clarifying question when the ask is ambiguous
  • Narrates evidence it did not produce
  • Drafts the per-client mapping at onboarding, the highest-leverage use, because a human reviews it

What it is never allowed to touch

  • Metric definitions · arithmetic · aggregation
  • Soft-delete and correction filtering
  • Access control and tenancy
  • Its own trust grade · causal conclusions · forecasts
  • Any write path, because the system is read-only

The four questions, answered

Question 1

A trustworthy answer

The definition lives in one governed place, derived from the Power BI model AYBI has already been paid to build. Same question → same intent → same SQL → same number. That is "the same question always gets the same answer" turned into a mechanism instead of a promise.

Messiness is solved in the model, not the agent. Two clocks everywhere: event_time for what happened in the yard, and knowledge_time (when the warehouse learned it). Any past answer replays exactly. When a number changes, the card says so and why.

Question 2

When a wrong answer would mislead

● CERTIFIED● QUALIFIED ● CLARIFY● REFUSE

Every answer carries a grade computed by deterministic checks: registry coverage, freshness against SLA, completeness, and whether the window has settled. Never model self-assessment, which cannot be calibrated or defended.

Certified answers are cleared for operational decisions. Qualified ones name their limitation. Ambiguous questions get exactly one question back. Where there is no basis, the system refuses and says what it would need, and each refusal is logged as a metric request, so limitations become roadmap.

Question 3

Affordable and fast, many clients

Canonical intents are what make caching possible at all, because two differently-worded questions collapse to one key. Free-form SQL cannot safely do that.

Four tiers: certified answer cache keyed on intent + client + knowledge-time watermark, so corrections landing invalidate exactly the affected answers and nothing else; intent cache, so the expensive model call happens only on genuinely novel phrasings; prompt cache for the registry block; precomputed aggregates on the hot path. Cost is logged per answered question, real tokens and dollars, not an estimate, so spend is visible enough to price and cap per client as a next step.

Question 4

Genuinely useful, not a demo

Measure the baseline before building. One week shadowing two planners and an ops manager: every question, who they asked, how long it took today. That single log becomes the build backlog, the test set and the baseline. Without it, "hours saved" is a number you invented.

Then report in AYBI's own unit: hours returned per week, share of questions answered without raising a BI ticket, and one tap on "did this change what you did?" The honest demo-ware test is week-6 weekly-active askers outside the project team. Sponsors always use it in week one.

Security, raised unprompted

  • Tenant from the authenticated session, never from the question. The query form has no field a tenant could occupy; the compiler takes the client's identity as a required argument, not a value the model could set. Asking for another terminal is a refusal, not a permission check that might pass
  • Row-level security inherited from the existing Power BI model, not rebuilt
  • Registry and intent are instructions; data values are evidence, never instructions, because vessel names and berth remarks are attacker-controlled text. A sanitizer screens every question before any model call and blocks known injection patterns outright, at zero cost because a blocked question never reaches the model. The exact planted injection string is blocked in testing, proven with a test that counts model calls, not assumed
  • The provider layer is swappable: direct API for simplicity, AWS Bedrock (eu-central-1) when a client needs EU-region data residency, or a local open-source model for clients who will not use a US vendor. The demo runs on whichever is configured; that choice is per-deployment, not fixed in the code
  • Cross-tenant probes are regression tests, not assurances

How it stays right

Five eval layers. Four are judged without a model, by exact comparison, a saved SQL snapshot, or a grade assertion, so the gate is credible: intent exact-diff · golden SQL snapshots · end-to-end against known truth · a must-refuse trap suite · narration faithfulness, the one layer an AI judge scores.

Layers 1 to 4 gate every prompt, model and registry change. Most teams test happy paths; testing that the system correctly declines is what turns refusal from a hope into a guarantee.

Honest boundaries

The demo runs on synthetic terminal data with deliberately seeded mess. It proves the logic, not the fit to any real terminal. The Power BI sync is parsed from a sample TMDL export, because Power BI Desktop is Windows-only and this was built on macOS. That is a laptop limitation, not an architectural one.

Rollout, where every gate is a number and nothing advances on enthusiasm. Wk 0 shadow planners → baseline. Wk 1 to 3 registry, compiler, evals, on one metric family and one terminal. Wk 3 to 5 AYBI engineers dogfood it; exit when they prefer it to the dashboard. Wk 5 to 9 client pilot with a human reviewing every answer, which is how the trust thresholds get calibrated rather than guessed. Wk 9 to 12 reviewer removed for the certified lane only; second client onboarded, and the exit KPI is onboarding days, not accuracy. If client two takes as long as client one, it is not a product yet, and we would say so.
